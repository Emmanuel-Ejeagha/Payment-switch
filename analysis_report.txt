MISMATCHES/BASEPATH ISSUES:

1. Version Mismatch: Frontend fetch URLs use API version prefix "v1" (e.g.,
   /api/proxy/identity/api/v1/auth/token, /api/proxy/payment/api/v1/payments),
   while backend .NET controllers use "v1.0" version prefix via the
   [Route("api/v{version:apiVersion}/[controller]")] attribute (e.g.,
   api/v1.0/auth/token, api/v1.0/payments). This creates a version skew
   where v1 ≠ v1.0 in the routing layer.

2. Service Name Prefix: Frontend fetch URLs embed explicit service name prefixes
   in the proxy path (e.g., /api/proxy/identity/..., /api/proxy/merchant/...,
   /api/proxy/payment/..., /api/proxy/ledger/..., /api/proxy/notification/...,
   /api/proxy/settlement/...). The backend .NET route templates do not include
   such service-name prefixes; routes are based on controller names only
   (e.g., AuthController, MerchantsController, PaymentsController). The proxy
   routes must strip or map these prefixes for backend routing to succeed.

3. BasePath /admin for Admin App: The admin Next.js application runs with
   basePath "/admin" (configured in next.config.js: basePath: "/admin"). All
   frontend fetch calls in the admin app go through an apiUrl() helper that
   prepends "/admin" (e.g., apiUrl("/api/proxy/identity/...") becomes
   "/admin/api/proxy/identity/..."). The backend .NET endpoints have no
   concept of this basePath prefix; the proxy routes in the admin app must
   account for this when forwarding to NEXT_PUBLIC_API_URL. Calls without the
   /admin prefix will 404 in the admin app's dev/production environment.

4. Controller Name vs Path Segment: Frontend URLs use "identity", "merchant",
   "payment", "ledger", "notification", "settlement" as path segments under
   the proxy (e.g., /api/proxy/identity/api/v1/...), while the .NET backend
   routes derive the route prefix from the C# controller class name suffix
   after "Controller" (e.g., AuthController → auth, PaymentsController →
   payments). Case and suffix handling may cause mismatches if not explicitly
   mapped in route configuration.

5. PublicPaymentsController Route Divergence: The PublicPaymentsController
   uses [Route("v1/payments")] attribute (not the base [Route("api/v{version}/[controller]")]),
   creating endpoints at v1/payments/intents, v1/payments/tokens, v1/payments/{id}/confirm,
   v1/payments/{id} while the standard PaymentController uses api/v1.0/payments,
   api/v1.0/payments/{id}. The frontend has both proxy calls
   (/api/proxy/payment/api/v1/payments/...) and direct calls
   (${process.env.NEXT_PUBLIC_API_URL}/payment/v1/checkout/links/...), creating
   two distinct URL spaces for payment operations.
