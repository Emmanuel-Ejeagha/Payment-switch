# Real-Time Payment Switch — Production Readiness TODO

Generated by a comprehensive codebase audit (Aug 2026). Audit-only session — no implementation changes were made.

---

## Executive Summary

### Overall Assessment

This is a genuinely credible, portfolio-worthy distributed payment system. Six Clean Architecture microservices (Identity, Merchant, Payment, Ledger, Notification, Settlement) over a shared kernel, with a working event-driven backbone (outbox → RabbitMQ → inbox → DLX), real gRPC service-to-service auth, optimistic concurrency, Testcontainers-based integration tests, two Next.js frontends fully wired to live APIs, and a real CI/CD pipeline that builds, tests, and ships Docker images. The domain-layer engineering — Payment state machine, Ledger double-entry with integer minor-unit money, idempotency replay, outbox/inbox/DLQ topology — is above average for a portfolio project.

However, several claims in the README overstate the implementation, and there are production-blocking financial-integrity, security, and auth-lifecycle gaps that must be closed before this can be called production-ready.

### Approximate Completion Level

Roughly **65–70% production-ready** by feature count (most core happy paths work end-to-end), but the missing 30% is concentrated in exactly the areas that matter most for a payment system: **financial correctness under failure, TLS, account lifecycle security, reconciliation, and testing**. The happy path is strong; the failure path is not.

### Strongest Areas

- **Payment domain**: guarded state machine, partial captures/refunds, card validation (Luhn/brand/expiry), replay idempotency, public secret-key API, card-token vault, payment links, subscriptions/invoices, webhook dispatch with HMAC signing + retry.
- **Ledger domain**: integer minor-unit `Money`, double-entry journal rows, currency guards, optimistic concurrency (`xmin`), atomic postings.
- **Messaging**: transactional outbox with lease-based multi-instance publishing; inbox dedup with unique `MessageId`; retry queue (TTL) + DLX + DLQ in Ledger & Notification; correlation-ID propagation via `BasicProperties.CorrelationId`.
- **Shared kernel**: Result pattern, value objects, guard clauses, rate limiting, security headers, correlation ID, request-size limits, service-token auth, gRPC resilience (circuit breaker + backoff).
- **Testing**: strong Domain/Application unit coverage (≈354 `[Fact]`/`[Theory]`), real-Postgres integration harness (Testcontainers).
- **Security hygiene**: no committed secrets; startup secret validation; BCrypt password/API-key hashing.
- **Frontend**: TypeScript strict, zero mocks — every screen hits real endpoints; good a11y; SignalR realtime notifications wired in both portals.

### Weakest Areas

- **Identity account lifecycle**: email verification, password reset/change, and account lockout are entirely absent.
- **Financial integrity under failure**: Ledger inbox is not atomic with posting (crash can double-post); Settlement's gRPC source is a stub producing fabricated figures; no unique constraint on settlement `BatchDate`.
- **Security**: no TLS anywhere (nginx, ingress, EC2, frontends); plaintext webhook secrets exposed in API/gRPC; unauthenticated Hangfire dashboard; default Grafana/RabbitMQ creds in k8s.
- **Messaging completeness**: 5 of 6 exchanges have zero consumers; 14+ events published into a void.
- **Observability**: no RabbitMQ trace propagation, no Grafana provisioning, hardcoded OTLP endpoint, no alerts.
- **Testing depth**: no E2E, no contract tests, no frontend tests, consumers/outbox/inbox/validators untested, 5 of 6 integration suites are health-check-only, no RabbitMQ in integration tests.
- **Docs**: README claims Event Sourcing, Saga, and OAuth2 that are not implemented.

### Biggest Production Risks

1. **Double-posting in Ledger** on message redelivery after a crash (financial loss / incorrect balances).
2. **Fabricated settlement figures** from the `GetDailyPayoutData` gRPC stub (payouts computed from current balance, fees always 0).
3. **Card data over plaintext HTTP** (checkout tokenization, public API, admin/merchant portals) — PCI-grade exposure.
4. **No email verification** — unverified identities can be created and used.
5. **Plaintext webhook secrets** returned to clients and over insecure gRPC channels.
6. **Duplicate settlement batches** via a missing `BatchDate` unique constraint.

### [ ] TASK-002 — Ledger Crash-Safe Idempotency (Prevent Double-Posting)

**Category:**
Financial Integrity / BUG

**Status:**
Partial (present but not crash-safe)

**Priority:**
P0 - Critical

**Why:**
The ledger is the financial source of truth. If the same `PaymentCapturedDomainEvent` is processed twice after a crash or redelivery, merchant balances and journal entries are duplicated — a direct financial-loss and incorrect-balance bug. The current inbox dedup is not atomic with the posting transaction.

**Current State:**
`Ledger.Infrastructure/Messaging/RabbitMQConsumerService.cs`:
1. L113-119: checks `InboxMessages` by `MessageId`; if a row with `ProcessedAt != null` exists → ack and skip.
2. L121-125: inserts the inbox row in its **own** DB scope/transaction.
3. L128-183: runs the posting handler (e.g., `CaptureFundsHandler`) in a **separate** transaction.
4. L185-191: a third scope marks `ProcessedAt`.
Crash between step 3 commit and step 4 → message redelivered → step 1 finds `ProcessedAt == null` → **handler re-runs → double posting**.
Additionally: `JournalEntry.CorrelationId` has **no unique constraint**, so a replayed post with the same correlation ID creates duplicate entries.

**Required:**
1. Make the inbox claim atomic with the business transaction: insert the inbox row as `InboxState = Processing` in the same DB transaction as the posting (single `SaveChanges`/`BeginTransaction`), then mark `Processed` after commit in a way that tolerates crash/redelivery.
2. Add a unique index on `JournalEntries.CorrelationId` as a DB-level backstop.
3. Keep the existing `MessageId` dedup but make the state machine `Processing → Processed` (never a raw re-run).
4. Verify idempotent behavior for all three consumed events (Authorized/Captured/Refunded).

**Affected Components:**
- Backend: Ledger.Infrastructure (RabbitMQConsumerService, Inbox*, UnitOfWork), Ledger.Application handlers
- Database: LedgerDb migrations (inbox state column, unique index)

**Dependencies:**
- Understanding of the existing outbox correlation ID flow (`OutboxPublisherService.cs:71` sets `MessageId = outbox Id`).

**Acceptance Criteria:**
- [ ] A simulated crash between posting-commit and mark-processed does not double-post on redelivery.
- [ ] `JournalEntry.CorrelationId` has a DB unique constraint.
- [ ] Inbox row lifecycle is single-transaction with the effect.
- [ ] Integration test proves the same `MessageId` delivered twice produces one posting.

**Evidence:**
- `src/Services/Ledger/Ledger.Infrastructure/Messaging/RabbitMQConsumerService.cs:113-191`
- `src/Services/Ledger/Ledger.Infrastructure/Inbox/InboxMessageConfiguration.cs:12` (unique `MessageId` only)
- `src/Services/Ledger/Ledger.Infrastructure/Persistence/Configurations/*` (no `CorrelationId` unique index)

### [ ] TASK-003 — Settlement Correctness (Fix `GetDailyPayoutData` Stub)

**Category:**
Financial Integrity / BUG

**Status:**
Bug (stub producing wrong figures)

**Priority:**
P0 - Critical

**Why:**
Settlement amounts are computed from fabricated data. `LedgerGrpcService.GetDailyPayoutData` ignores the requested `date`, sets `gross_volume = current AvailableBalance` (not daily gross volume), and returns `fees = 0` always. `TriggerSettlementHandler` feeds these numbers directly into `SettlementBatch`/`Payout` rows and marks the batch `Completed`. Settlement totals are therefore wrong by construction — a direct financial-correctness defect.

**Current State:**
- `src/Services/Ledger/Ledger.API/Services/LedgerGrpcService.cs:37-57` — stub implementation (date ignored, gross = current balance, fees = 0).
- `src/Services/Settlement/Settlement.Application/.../TriggerSettlementHandler.cs:55-59` — consumes the stub output.
- Ledger has no aggregation of daily captured/refunded/fee amounts per merchant; balances are denormalized, journal entries exist but are not summed per day.
- Settlement marks batch `Completed` synchronously in the same handler (`Complete()`, line 70); `processing` status is dead code.

**Required:**
1. Implement real daily payout data in Ledger: sum journal entries (`Capture` debits) per merchant per `date`, compute fees from `FeesIncome` entries, and subtract refunds for that day.
2. Return correct gross/fees/currency per merchant for the requested date (not current balance).
3. Add a Settlement-side reconciliation assertion before `Complete()` (e.g., validate gross matches ledger totals; log/alert on mismatch instead of silently completing).
4. If ledger aggregation is expensive, cache or index `JournalEntries(LedgerAccountId, Timestamp)` (see also TASK-017).

**Affected Components:**
- Backend: Ledger.API (LedgerGrpcService), Ledger.Application (new aggregation query), Settlement.Application (TriggerSettlementHandler), gRPC contract `src/Protos/ledger.proto`
- Database: LedgerDb index

**Dependencies:**
- TASK-002 (idempotent, non-duplicated journal entries — otherwise daily sums double-count).

**Acceptance Criteria:**
- [ ] `GetDailyPayoutData(date)` returns gross = Σ captures − Σ refunds for that date, and correct fees.
- [ ] Settlement batch totals match ledger daily sums.
- [ ] Mismatch between settlement totals and ledger totals is detected and surfaced (not silently completed).
- [ ] Unit tests for the aggregation; integration test comparing settlement output to ledger journal.

**Evidence:**
- `src/Services/Ledger/Ledger.API/Services/LedgerGrpcService.cs:37-57`
- `src/Services/Settlement/Settlement.Application/Features/Command/TriggerSettlement/TriggerSettlementHandler.cs:55-70`

### [ ] TASK-006 — Merchant Webhook Secret: Stop Exposing / Encrypt at Rest

**Category:**
Security

**Status:**
Partial (badly)

**Priority:**
P0 - Critical

**Why:**
The merchant webhook signing secret is stored **plaintext**, returned in merchant API responses, and transmitted over insecure gRPC. Anyone with read access to the merchant endpoint (or network visibility of the gRPC channel) can forge webhook deliveries. Secrets must be encrypted at rest, never returned to clients after generation, and only delivered where strictly needed.

**Current State:**

- Rotation exists (`POST /webhook-secret/rotate`) but with no dual-secret grace window or old-secret history.

**Required:**
1. Encrypt `WebhookSecret` at rest (e.g., AES-GCM with a key from config/secrets) or store only a hash for verification.
2. Remove `WebhookSecret` from all API DTOs/responses (never return after creation; only return once on rotate like API keys).
3. Secure the gRPC channel or gate secret delivery behind the existing `ServiceOnly` policy (already present) + TLS (TASK-004).
4. Add dual-secret rotation (old + new valid during a grace window) to avoid breaking live webhook consumers.

**Affected Components:**
- Backend: Merchant.API (DTOs/controllers), Merchant.Domain, Merchant.Infrastructure, Merchant gRPC, Payment `WebhookDispatcher`
- Database: MerchantDb migration (secret storage)

**Dependencies:**

**Acceptance Criteria:**
- [ ] `WebhookSecret` never appears in any HTTP response.
- [ ] Secret encrypted at rest; decrypt only inside webhook signing path.
- [ ] Rotation supports a grace window for the previous secret.
- [ ] Tests assert the secret is not returned and old secret still verifies during grace.
